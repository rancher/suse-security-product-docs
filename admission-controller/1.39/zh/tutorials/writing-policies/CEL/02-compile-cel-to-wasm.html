Compile CEL to WebAssembly

This is an experimental feature available since Admission Controller v1.39.0.

In this tutorial, you compile a Kubernetes ValidatingAdmissionPolicy into a WebAssembly module with kwctl. You then inspect the module and prepare it for deployment as a ClusterAdmissionPolicy.

Why compile CEL to WebAssembly?

The alternative approach with cel-policy policy runs CEL code using the official CEL Go interpreter. See Using cel-policy for how that policy works.

That approach has two drawbacks:

  • Size: The cel-policy policy bundles the entire CEL runtime and the Kubernetes CEL libraries, even when a policy uses only some of them. As a result, the WebAssembly module is large, which increases the PolicyServer startup time.

  • Portability: The CEL code lives inside the Admission Controller policy manifest. This is good for prototyping because there is no build step. But it makes the policy hard to share. The manifest also carries deployment details such as the target namespaces and objects, the enforcement mode, and more.

Alternatively, when you compile CEL to WebAssembly, you produce a smaller and more efficient module that you can share and reuse across different deployments.

Admission Controller uses the ferricel open source project to compile a Kubernetes ValidatingAdmissionPolicy into a specialized WebAssembly module.

As a comparison, the WebAssembly file produced by this compiler is around 1.5MiB, while the one produced by the cel-policy is 14MiB.

The compiled module is also much faster. See Performance for benchmark results.

Prerequisites

  • The kwctl CLI tool.

  • A ValidatingAdmissionPolicy that cel-policy can run, and its matching ValidatingAdmissionPolicyBinding.

Compile a policy

You compile a policy from the ValidatingAdmissionPolicy and its binding with the kwctl scaffold vap command.

Before Admission Controller v1.39.0, this command converted a ValidatingAdmissionPolicy into a ClusterAdmissionPolicy that used the cel-policy policy. From v1.39.0, the command can also produce a .wasm file when you provide the --compile-to-wasm flag.

Start from this ValidatingAdmissionPolicy definition, in a file named vap-with-params.yml:

vap-with-params.yml 
apiVersion: admissionregistration.k8s.io/v1
kind: ValidatingAdmissionPolicy
metadata:
  name: "vap-test"
spec:
  failurePolicy: Fail
  matchConstraints:
    resourceRules:
      - apiGroups: ["apps"]
        apiVersions: ["v1"]
        operations: ["CREATE", "UPDATE"]
        resources: ["deployments", "deployments/scale"]
  paramKind:
    apiVersion: v1
    kind: ConfigMap
  validations:
    - expression: "object.spec.replicas <= int(params.data.maxReplicas)"
      message: "too many replicas"

And this ValidatingAdmissionPolicyBinding, in a file named vap-binding-params.yml:

vap-binding-params.yml 
apiVersion: admissionregistration.k8s.io/v1
kind: ValidatingAdmissionPolicyBinding
metadata:
  name: "kw-scaffold-demo"
spec:
  policyName: "vap-test"
  validationActions: [Deny]
  matchResources:
    namespaceSelector:
      matchLabels:
        kubernetes.io/metadata.name: default
  paramRef:
    name: "replica-limit-override"
    namespace: "test"
    parameterNotFoundAction: Deny

Compile them with this command:

kwctl scaffold vap \
  --policy vap-with-params.yml \
  --binding vap-binding-params.yml \
  --compile-to-wasm policy.wasm

The command produces two files:

  • policy.wasm: The ValidatingAdmissionPolicy compiled to WebAssembly.

  • metadata.yml: The standard metadata file for Admission Controller policies.

The metadata.yml file looks like this:

metadata.yml 
rules:
- apiGroups:
  - apps
  apiVersions:
  - v1
  resources:
  - deployments
  - deployments/scale
  operations:
  - CREATE
  - UPDATE
annotations:
  io.kubewarden.policy.title: kw-scaffold-demo
mutating: false
backgroundAudit: true
executionMode: ferricel
policyType: kubernetes
contextAwareResources:
- apiVersion: v1
  kind: ConfigMap
hostCapabilities:
- kubernetes/get_resource
- kubernetes/list_resources_all
- kubernetes/list_resources_by_namespace

The command derives these metadata values from the ValidatingAdmissionPolicy and ValidatingAdmissionPolicyBinding definitions.

The command also prints a ClusterAdmissionPolicy definition to standard output:

Generated ClusterAdmissionPolicy 
apiVersion: policies.kubewarden.io/v1
kind: ClusterAdmissionPolicy
metadata:
  name: kw-scaffold-demo
spec:
  module: file:///path/to/policy.wasm
  settings:
    failurePolicy: Fail
    paramKind:
      apiVersion: v1
      kind: ConfigMap
    paramRef:
      name: replica-limit-override
      namespace: test
      parameterNotFoundAction: Deny
  rules:
  - apiGroups:
    - apps
    apiVersions:
    - v1
    resources:
    - deployments
    - deployments/scale
    operations:
    - CREATE
    - UPDATE
  mutating: false
  contextAwareResources:
  - apiVersion: v1
    kind: ConfigMap
  mode: protect
  namespaceSelector:
    matchLabels:
      kubernetes.io/metadata.name: default

This is the ClusterAdmissionPolicy definition that you can deploy in a Kubernetes cluster.

  • Change the module URL to the location where you publish the policy.

  • The settings section passes parameter metadata to the compiled policy. At runtime, the policy uses this metadata to find the ConfigMap or other resource. It also defines the failure mode for misconfigurations and CEL evaluation errors.

All these settings are derived from the ValidatingAdmissionPolicy specification.

Next, like with any type of Admission Controller policy, annotate the WebAssembly module with this command:

kwctl annotate -m metadata.yml -o annotated.wasm policy.wasm

Run the policy

Use kwctl run to test the policy locally before you deploy it. See 针对策略作者的测试 for the request and settings files that kwctl run needs, and for how to write automated tests.

To distribute the policy, push it to an OCI registry with kwctl push:

kwctl push annotated.wasm registry.example.com/policies/kw-scaffold-demo:v0.1.0

Then set the module field of the ClusterAdmissionPolicy to the registry URL, for example registry://registry.example.com/policies/kw-scaffold-demo:v0.1.0. See 分发策略 for more details.

The paramRef of the binding refers to a replica-limit-override ConfigMap in the test namespace. The policy reads maxReplicas from this ConfigMap at evaluation time. Before deploying the ClusterAdmissionPolicy in cluster, create the Namespace and the ConfigMap. Put them in a file named replica-limit-override.yml:

replica-limit-override.yml 
apiVersion: v1
kind: Namespace
metadata:
  name: test
---
apiVersion: v1
kind: ConfigMap
metadata:
  name: replica-limit-override
  namespace: test
data:
  maxReplicas: "1"

Apply the file:

kubectl apply -f replica-limit-override.yml

The binding sets parameterNotFoundAction: Deny. If the ConfigMap is missing, the policy rejects all CREATE and UPDATE operations on Deployments in the default namespace.

All CEL policies need access to the Kubernetes API server. Policies with parameters need access to the referenced resources, such as the ConfigMap in this example.

A policy without parameters still needs to query the API server for the Namespace of the object being evaluated.

Kubernetes ValidatingAdmissionPolicy uses CEL in this way. Therefore, deploy CEL policies, both compiled and interpreted, only as ClusterAdmissionPolicy resources.

The benchmark used the kwctl bench command. It recorded the interaction with the Kubernetes API server and replayed it to avoid network latency and other external factors.

The WebAssembly policy produced by the ferricel compiler runs one to two orders of magnitude faster than the interpreted cel-policy.

Limitations

The ferricel compiler currently passes the full CEL compliance suite and supports the cel-go and Kubernetes extensions. However, it’s still an experimental project and might not yet cover all edge cases.

The full status of the ferricel compiler can be found in the official documentation: CEL compliance.

If your compiled policy does not behave as expected, file an issue on the ferricel bug tracker.
