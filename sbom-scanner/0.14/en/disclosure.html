Security disclosure

The SUSE Security Team appreciates investigative work on security vulnerabilities carried out by well-intentioned, ethical security researchers. SUSE Security Vulnerability Scanner follows the practice of responsible disclosure to best protect Vulnerability Scanner’s user base from the impact of security issues. On Vulnerability Scanner’s side, this means:

  • Vulnerability Scanner responds to security incidents on priority.

  • Vulnerability Scanner releases fixes for issues as soon as is practical, prioritizing by risk.

  • Vulnerability Scanner always transparently lets the community know about any incident that affects them.

If you have found a security vulnerability in SUSE Security Vulnerability Scanner, the easiest way to report a vulnerability is through the Security tab on GitHub for the specific repo. This mechanism allows maintainers to communicate privately with you, and you don’t need to encrypt your messages.

Alternatively, you can disclose it responsibly by emailing cncf-kubewarden-maintainers@lists.cncf.io in an unencrypted message. Please don’t discuss potential vulnerabilities in public without validating with us first.

You can also come talk in our slack-room on the Kubernetes Slack server.

On receipt the SUSE Security Team:

  • Reviews the report, verifies the vulnerability and responds with confirmation and/or further information requests.

  • After addressing the reported security bug, the SUSE Security Team notifies the Researcher, who is then welcome to optionally disclose publicly.

What information to provide

You need to provide the information below for the report to be timely, and effectively analyzed. Reports that miss the required information might be considered AI generated spam or reviewed with a lower priority.

  • Project name and version where the issue was observed. If the issue was observed on the source code, the link to the specific code in GitHub instead.

  • Description of the problem.

  • Type of the issue and impact when exploited.

  • Steps to reproduce.

  • A valid proof of concept (POC) exploit (only on a valid system that you are authorized to perform such proof). A working POC is now mandatory as a proof of work (POW) to reduce the noise of AI generated low quality reports.

  • It’s mandatory to inform if AI tools were used to find the issue being reported, to automate or to write the report, POC code or possible patch. If this was the case, then inform which AI tools and models were used.

The more information you provide, the faster we will be able to reproduce the issue and address your concerns more effectively.

Please, refer to the community repository to find more about the project Governance and Security Policy.
